# Questions to Ask a Developer About Security Before You Hire Them

Most non-technical founders can't evaluate a developer's code directly, but they can evaluate how that developer talks about security — and how someone answers a direct security question tells you a lot about how they'll actually build. This is a practical set of questions, along with what a genuinely competent answer sounds like versus a vague one that should give you pause.

## "How do you handle user passwords and authentication?"

**A good answer** mentions using an established authentication library or service (rather than custom-built password handling), proper password hashing (bcrypt, argon2, or similar — never storing passwords in plain text or with weak hashing), and some mention of rate limiting on login attempts to prevent brute-force attacks.

**A vague or concerning answer** is something like "we'll handle that securely" with no specifics, or a developer who seems surprised by the question, suggesting they haven't thought about it as a distinct concern separate from just "making login work."

## "How do you prevent one customer from seeing another customer's data?"

This is the single most important question for any application handling multiple customers or user accounts. **A good answer** describes explicit checks — at the database query level, not just hidden buttons in the interface — that verify a logged-in user actually owns or has permission to access the specific data being requested, for every relevant request, not just the obvious ones.

**A concerning answer** relies entirely on "we just don't show them the link" (hiding functionality in the UI without enforcing it on the backend is not access control) or can't clearly explain how their system checks ownership at all.

## "What happens to user input before it touches the database or gets displayed back to other users?"

This question surfaces whether a developer understands injection attacks and cross-site scripting, two of the most common and most damaging web vulnerabilities. **A good answer** mentions using parameterized queries or an ORM that handles this automatically (rather than building SQL queries by concatenating strings), and either escaping or sanitizing user-generated content before displaying it elsewhere on the site.

**A concerning answer** is uncertainty about what these terms mean, or an assumption that "the framework handles all of that automatically" without being able to explain what specifically it handles.

## "How are API keys, database credentials, and other secrets managed?"

**A good answer** describes environment variables or a dedicated secrets management service, with secrets never committed directly into the code repository, and different credentials used for development versus production environments.

**A concerning answer** involves secrets hardcoded directly in the codebase (a strong sign that if you ever look at the code, you'll find your production database password sitting in a file that's been committed to version control, sometimes even a public repository) or no clear separation between development and production credentials.

## "What's your process for keeping dependencies updated?"

Every website built with modern tools depends on third-party libraries, some of which will have security vulnerabilities discovered over their lifetime. **A good answer** describes a regular process — automated dependency scanning, periodic review, prompt patching for anything flagged as high severity — not a one-time setup with no ongoing plan.

**A concerning answer** is "we'll update things if we notice a problem," which usually means nobody's actually watching for problems until something goes wrong publicly.

## "If there's a security incident after launch, what's the response process?"

**A good answer** includes some plan for detection (monitoring or logging that would reveal unusual activity), a communication plan (who gets notified, including you as the client, and how quickly), and a general sense of containment steps (rotating credentials, patching the specific vulnerability, assessing what data may have been affected).

**A concerning answer** is essentially "that shouldn't happen," which reflects overconfidence rather than the honest acknowledgment that security incidents happen even to careful teams, and preparedness matters more than assuming it won't happen to you.

## "Do you test for these issues before launch, and how?"

**A good answer** describes at least basic security testing practices appropriate to the project's scale — this could range from manual review against a known checklist (the OWASP Top 10 is a widely used reference point) for a smaller project, to automated security scanning tools and possibly a third-party security review for a larger or more sensitive application.

**A concerning answer** is that security testing wasn't planned as a distinct activity at all, and the assumption is that "if it works, it's secure," which conflates functional correctness with security, two genuinely different properties.

## What these questions are really testing for

None of these questions require you to understand the technical answer in full detail. What they test for is whether security is something the developer has thought about as a distinct, ongoing concern versus something they assume happens automatically or plan to address only if something goes wrong. The specificity and confidence of the answer matters more than whether you personally understand every technical term used.

## When to bring in extra scrutiny

For a simple informational website with no user accounts, payment processing, or sensitive data, a lighter version of this conversation is appropriate — the stakes are genuinely lower. For anything handling customer accounts, payment information, or sensitive personal data, these questions deserve real, specific answers, and it's reasonable to ask for a written summary of security practices as part of a proposal, or to have a technical advisor review the answers if you don't have that expertise in-house yourself.

## Common mistakes businesses make in this evaluation

- **Assuming a developer's portfolio or client list is a proxy for security competence.** A visually polished portfolio says nothing about backend data handling practices, which are invisible from the outside.
- **Not asking these questions until after a problem occurs**, when the cost of fixing security issues retroactively — including potential data breach disclosure and remediation — is far higher than addressing them during development.
- **Treating "we use [popular framework]" as a complete answer.** Frameworks provide tools and defaults that help, but a developer still has to use them correctly; the framework name alone doesn't guarantee competent implementation.
- **Skipping this conversation for smaller projects** on the assumption that a small site isn't a target. Small business sites are attacked constantly by automated tools scanning for common vulnerabilities, regardless of the business's size.

## Where this fits into a broader evaluation

Security competence tends to correlate with general engineering discipline — a developer who's thoughtful about access control and input handling is usually also thoughtful about code organization, testing, and maintainability. These questions are a genuinely useful proxy for overall quality, not just a narrow security checklist. If you're evaluating a broader [custom software development](/services/custom-software-development) partner rather than a single project, the same questions are worth asking about their standard practices across projects, not just the one you're currently discussing. ## Frequently asked questions

**Should we ask for a formal security audit before launch?**
For anything handling payments or sensitive personal data, a third-party security review is a reasonable investment before launch. For simpler sites, a careful internal review against a known checklist like the OWASP Top 10 is often proportionate to the risk.

**How do we evaluate these answers if we're not technical ourselves?**
The specificity and confidence of the answer matters more than your own technical understanding of every term. A developer who can explain their reasoning clearly, even in approachable language, is a better sign than one who deflects with jargon or vague reassurance.

**Is it reasonable to ask for references specifically about security practices?**
Yes — asking a past client whether they ever experienced a security incident, and how it was handled if so, is a legitimate and useful reference question that most developers should be comfortable with you asking.

**What if the developer we're considering doesn't know the answer to one of these questions?**
Not knowing one specific technical detail isn't automatically disqualifying, but an inability to engage seriously with the underlying concern — dismissing the question or offering vague reassurance instead of a real answer — is a meaningful red flag.
